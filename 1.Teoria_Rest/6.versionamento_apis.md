# Versionamento de APIs

---

## 1. Por que Versionar uma API?

As APIs não são estáticas; elas precisam evoluir para acompanhar as mudanças do mundo real (ex.: novas regras de negócio).

- **Impacto nas aplicações:** Mudanças na lógica exigem alterações nos _endpoints_ e na assinatura dos contratos.
- **Proteção aos clientes:** Sem versionamento, uma atualização quebra imediatamente os sistemas que consomem a API (como aplicativos _mobile_ ou integrações de terceiros).
- **Ciclo de migração:** Permite notificar os clientes sobre mudanças, conceder um prazo para adaptação e descontinuar versões antigas de forma controlada.

---

## 2. Estratégias de Versionamento

Abaixo estão as principais abordagens utilizadas no mercado, organizadas da menos recomendada para a mais recomendada pelo instrutor:

### 2.1. Por Subdomínio (_Subdomain_)

- **Como funciona:** A versão é inserida antes do nome do _host_ na URL.
    - _Exemplo:_ `https://v1.localhost:8080/api/recurso/1`
- **Avaliação:** **Não recomendada.** Embora utilizada em alguns cenários, torna a manutenção do código e o gerenciamento dos clientes consideravelmente mais complexos.

### 2.2. Por Query Param (_Query Parameter_)

- **Como funciona:** A versão é passada como um parâmetro de consulta na URL.
    - _Exemplo:_ `{{baseURL}}/api/recurso/1?version=1.0`
- **Avaliação:** **Não recomendada.** Aumenta o tamanho da URL e exige que o cliente monte a requisição de forma dinâmica. Embora simples de implementar no servidor, é mais complexa para manter e consumir.

### 2.3. Por Media Type / Content Negotiation (`Accept` Header)

- **Como funciona:** Utiliza o cabeçalho HTTP `Accept` para especificar a versão desejada junto ao formato de mídia (Vendor MIME Type).
    - _Exemplo:_ `Accept: application/vnd.suaapi.v1+json`
- **Avaliação:** **Não recomendada.** Pouco prática no dia a dia, difícil de manter e propensa a erros ou confusões por parte de quem realiza as requisições.

### 2.4. Por Custom Header (_Header Param_)

- **Como funciona:** Cria-se um cabeçalho HTTP personalizado exclusivo para trafegar o número da versão.
    - _Exemplo:_ `api-version: 1`
- **Avaliação:** **Não recomendada.** É uma alternativa mais limpa que o _Media Type_, mas ainda exige configurações extras de cabeçalho por parte do consumidor.

### 2.5. Por Path Param (_URI Versioning_) — ⭐ Recomendada

- **Como funciona:** A versão é incorporada diretamente no caminho (rota) da URL.
    - _Exemplo:_ `{{baseURL}}/api/recurso/v1/1`
- **Avaliação:** **Altamente recomendada.** É a abordagem mais inteligente, explícita e prática tanto para quem desenvolve quanto para quem consome a API.

---

## 3. Benefícios e Boas Práticas de Governança

O versionamento adequado garante a **evolução estável e linear** da API sem quebrar os clientes ativos.

- **Comunicação proativa:** Avise os consumidores com antecedência sobre alterações futuras e datas de encerramento de suporte (_sunset_).
- **Uso de Headers informativos na resposta:** Adicione cabeçalhos na _response_ alertando que o _endpoint_ atual está depreciado (_deprecated_), indicando a nova versão recomendada e a data limite para migração.
- **Previsibilidade:** Permite que as equipes clientes planejem suas correções e migrem para a nova versão dentro de um cronograma seguro.
